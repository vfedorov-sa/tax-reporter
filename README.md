# tax-reporter

Сервис подготовки справок об оплате медицинских услуг для представления в налоговый
орган (форма по КНД 1151156). Забирает заявки, приводит их к доменной модели,
прогоняет контрольные соотношения, собирает PDF по бланку и отправляет пакет в
приёмный шлюз.

Публичная версия рабочего проекта. Бланк, справочник клиник и тестовая выгрузка
синтетические: реальные справки содержат ФИО, ИНН, даты рождения и реквизиты
документов пациентов, в том числе несовершеннолетних, — таким данным в репозитории
не место. Подпись тоже не приложена, демонстрационный росчерк рисует
`scripts/make_signature.py`.

## Что делает

До сервиса пакет собирался вручную: оператор переносил данные из формы в бланк,
глазами сверял ИНН и суммы и отправлял справки по одной. Ошибку находили уже по
отказу из налоговой, через несколько дней. Сервис закрывает весь путь одним
прогоном и, главное, отклоняет заведомо непроходные справки до отправки, называя
причину.

```
выгрузка заявок ──► нормализация ──► контрольные ──► сборка PDF ──► пакет ──► шлюз
   (CSV / API)        (pandas)       соотношения      (pypdf,       (zip +
                                                     reportlab)   manifest)
                                          │
                                          └──► отчёт: что принято, что нет и почему
```

## Запуск

```bash
pip install -e ".[dev]"
cp .env.example .env
uvicorn tax_reporter.api:app --reload
```

```bash
curl -F file=@samples/requests.csv "localhost:8000/v1/batches?submit=false"
```

В ответ приходит разбор всей выгрузки: по каждой заявке — принята она или нет и с
какими замечаниями. На тестовой выгрузке из восьми строк проходят три.

В Docker:

```bash
docker build -t tax-reporter .
docker run --rm -p 8000:8000 -v "$PWD/out:/data/out" tax-reporter
```

## Эндпоинты

| Метод  | Путь                                          | Описание                                    |
|--------|-----------------------------------------------|---------------------------------------------|
| `GET`  | `/healthz`, `/readyz`                         | живость и готовность, список бланков        |
| `GET`  | `/v1/templates`                               | отчётные годы, под которые есть бланк       |
| `POST` | `/v1/certificates/validate`                   | проверки без генерации PDF                  |
| `POST` | `/v1/batches`                                 | выгрузка файлом, `?submit=false` — вхолостую |
| `POST` | `/v1/batches/from-intake?tax_year=2025`       | забрать заявки из источника и обработать    |
| `GET`  | `/v1/batches/{id}`                            | отчёт по пакету                             |
| `GET`  | `/v1/batches/{id}/documents/{filename}`       | готовая справка                             |

`/v1/certificates/validate` отдаёт те же коды ошибок, что и пакетная обработка,
поэтому форма приёма заявок может проверять данные сразу при вводе, а не узнавать
о проблеме в конце месяца.

## Контрольные соотношения

Проверки уровня поля (длина, тип, диапазон) делает pydantic при разборе. В
`validation.py` остаются межполевые правила — то, что нельзя проверить, глядя на
одно значение:

| Код                          | Правило                                                        |
|------------------------------|----------------------------------------------------------------|
| `CLINIC_INN`, `CLINIC_KPP`   | контрольный разряд ИНН организации, формат КПП                 |
| `TAXPAYER_INN`, `PATIENT_INN`| два контрольных разряда ИНН физлица                            |
| `AMOUNT_EMPTY`               | хотя бы одна из сумм по кодам услуг «1» и «2» положительна     |
| `AMOUNT_OVER_LIMIT`          | расходы по коду «1» сверх предела вычета — предупреждение      |
| `PERIOD_AHEAD`               | отчётный год не может быть позже даты выдачи                   |
| `PERIOD_STALE`               | за период старше трёх лет вычет уже не заявить                 |
| `ISSUED_IN_FUTURE`           | дата выдачи не в будущем                                       |
| `PATIENT_DUPLICATES_TAXPAYER`| пациент совпал с налогоплательщиком при признаке «разные лица» |
| `PATIENT_DOCUMENT`           | у пациента, отличного от плательщика, документ обязателен      |
| `DOCUMENT_KIND_MINOR`        | до 14 лет документ — свидетельство о рождении, не паспорт      |
| `DOCUMENT_KIND_ADULT`        | с 14 лет свидетельство о рождении личность не удостоверяет     |
| `DOCUMENT_ISSUED_LATER`      | документ не может быть выдан позже самой справки               |
| `DUPLICATE_NUMBER`           | номер уникален в пределах клиники, года и корректировки        |

Ошибки останавливают справку, предупреждения попадают в отчёт и не мешают отправке.
Предел социального вычета зависит от периода: 120 000 ₽ до 2024 года, 150 000 ₽ с 2024-го.

## Бланк и карта полей

Форма меняется почти каждый год, поэтому её описание вынесено из кода в JSON рядом
с PDF: где на странице лежит ячейка, откуда берётся значение и как его
отформатировать.

```json
"tp_birth_date": {
  "page": 0, "x": 85, "y": 511, "width": 110, "height": 15,
  "source": "taxpayer.birth_date", "format": "date"
}
```

Новый отчётный год — это новая пара файлов в `templates/`, а не правка рендерера.
Обе половины порождает `scripts/build_template.py` из одного описания, так что
геометрия в бланке и в карте не могут разойтись.

Вторая страница печатается только если лечился не сам налогоплательщик: признак
«одно лицо» и поле «справка составлена на N страницах» считаются от наличия блока
пациента, а лишняя страница удаляется из готового документа.

### Почему значения рисуются, а не подставляются в поля формы

Первым заходом значения шли прямо в поля AcroForm через `update_page_form_field_values`.
На кириллице это не работает: в `/DA` бланка стоит Helvetica, у которой нет нужных
глифов, и справка открывалась либо пустой, либо с «кракозябрами» — смотря чем её
открыть. Подставить вместо Helvetica вшитый TTF тоже не выходит: reportlab кладёт
подмножество шрифта без `/Encoding`, и сопоставить Unicode с кодами символов
нечем.

Поэтому поля бланка схлопываются, а значения выводятся наложением тем же шрифтом,
которым нарисован сам бланк, — тем же механизмом, что и подпись. Побочный плюс: на
выходе получается плоский PDF без редактируемых полей, который шлюз принимает без
оговорок.

## Устройство

| Модуль        | Отвечает за                                                         |
|---------------|----------------------------------------------------------------------|
| `models.py`   | доменная модель: справка, клиника, физлицо, документ                 |
| `inn.py`      | контрольные разряды ИНН и формат КПП                                 |
| `validation.py` | контрольные соотношения, ошибки и предупреждения                   |
| `intake.py`   | разбор грязной выгрузки: суммы, даты, ФИО, справочник клиник         |
| `templates.py`| бланки, привязка полей и форматирование значений                     |
| `rendering.py`| сборка PDF и наложение подписи                                       |
| `gateway.py`  | упаковка в zip и отправка, локально или по HTTP                      |
| `pipeline.py` | оркестрация и отчёт по пакету                                        |
| `api.py`      | HTTP-интерфейс                                                       |

Модель намеренно строгая: `extra="forbid"`, суммы в `Decimal`, признак пациента
выводится из наличия блока, а не хранится отдельным полем, которое может
разойтись с данными. Весь разбор пользовательского ввода живёт в `intake.py`,
поэтому дальше по конвейеру данные уже нельзя собрать некорректно.

## Тесты

```bash
pytest
ruff check .
```

95 тестов: контрольные разряды ИНН на испорченных значениях, каждое контрольное
соотношение по отдельности, разбор сумм и дат во всех встречавшихся форматах,
снятие повторных заявок, число страниц и попадание значений на нужную страницу
готового PDF, работа пакета от выгрузки до zip и HTTP-слой целиком.
